# 工作流

## 初始化

编排者和项目负责人明确用户、使用场景、第一版验收标准和范围。根据这些约束拟定技术方案，记录需要负责人决定的事项。确认后填写 [项目规则](../PROJECT.md)，按可验证的交付拆出 GitHub Issue。每个 Issue 写清目标、范围、验收标准、依赖、风险和可能修改的目录或模块。

## 风险分级

编排者在拆 Issue 时先给出等级和理由。开发时发现影响范围扩大，在 Issue 更新风险及原因，再按新等级安排审查。风险取变更影响中的最高一项。涉及项目专属门槛时由项目负责人确认，影响不清楚时先核实，再发合并任务。

| 等级 | 常见情况 | 合并前需要 |
| --- | --- | --- |
| 低 | 文案、注释、与产品行为无关的测试补充 | 适用的 CI 和一次轻量独立检查 |
| 中 | 普通功能、业务逻辑修改、范围明确的重构 | 适用的 CI 和独立审查，验证验收标准与回归风险 |
| 高 | 权限、敏感数据、生产操作、不可逆迁移、核心架构 | 独立审查、关键风险验证和项目负责人针对本次合并的授权。项目规则可要求跨模型复审 |

## 每天开工

1. 读取开放 Issue、关联 PR、审查和 CI。识别待返工、待审、待授权及被依赖阻塞的工作。
2. 先处理阻塞关键交付的事项，再按对第一版验收目标的影响排序。依赖已满足、代码和共享资源范围互不影响的任务可并行。共享数据结构、迁移、公共接口和同一文件的任务排先后。
3. 给出今日目标、可做的任务和阻塞项，为每个要启动的 Issue 生成可复制的[任务书](task-briefs.md)。拆 Issue 时可以附一份开发提示词草稿；开工时按最新 Issue 和 PR 更新已有实现、范围和依赖。没有草稿时直接从 GitHub 生成。由负责人启动选定的 AI 助手。

## 编排者会话接力

在[编排者指令模板](orchestrator-instructions.md)填入目标仓库和规则链接。选用能获取当前 GitHub 证据的 AI 工具，或由负责人提供证据。总控会话处理「开工」和并行安排。每个启动的 Issue 使用独立会话，首次给 Issue 链接；有开发提示词草稿时可一并提供。

1. **收到开发回执**：核对 PR、当前 head SHA、验收项、测试和未完成项。具备审查条件时生成独立审查任务书；发现交付缺项时说明需要补什么。
2. **收到审查回执**：核对被审 SHA 是否为当前 head，且独立审查、适用检查和阻塞有记录。需修复时生成返工任务书，按新提交安排复审；缺少证据、审查过期或检查未就绪时说明如何补齐。满足条件时生成合并任务书，说明还需哪项授权。
3. **记录进度**：开发和审查证据写回对应 Issue 或 PR。会话用于传递提示词和回执；GitHub 用于确认当前状态。无法访问 GitHub 时，向负责人索取缺少的最小证据，标明哪些状态还未核实。

## 从 Issue 到验收

1. **待办 → 开发中。** 在 Issue 记录分工、依赖和风险。开发者用独立分支或工作区实施，开 PR 并在模板里记录 Issue、测试结果和遗留限制。
2. **待审 → 返工或通过。** 编排者核对实际 diff 和 CI 后发审查任务。独立审查者自行读 Issue、差异、检查结果并验证关键场景，将审查者身份、被审提交 SHA、阻塞问题及结论记在 PR。开发者修正后，把受影响的内容交回复审。
3. **待合并 → 已合并。** 编排者在 GitHub 记录拟合并顺序和授权状态。指定合并人按顺序逐个处理，核对正确的目标分支、当前 PR 提交的审查证据、所需检查、未解决的阻塞和授权范围。前一项合并影响后一项时，先重新验证后一项。可使用支持预期提交 SHA 的合并命令，防止检查之后 PR 发生更新。
4. **已合并 → 已验收。** 按 Issue 的验收标准验证实际效果，记录证据后关闭 Issue。如果工程已合入、只剩人工验收，Issue 保持打开，记录验收人和具体动作，同时退出开发队列，并移除已有的可开发标签。需要跟进的工作用关联 Issue 追踪。

项目负责人可在项目规则中预先授予指定合并人常规低、中风险合并权限。高风险合并需记录本次 PR 与当前提交对应的授权。GitHub 上用 Issue 分工、PR 状态、审查、检查和交接记录判断进度，需要时用标签标记当前阶段。

## 同一 Integrator 连续合并

完成一个 PR 后，项目负责人可在同一个 Integrator 会话中说“继续合并下一个符合条件的 PR”，无需另开 Agent 或维护集中队列。Integrator 从 GitHub 当前开放 PR 中，根据依赖和交付优先级选择下一个**已通过独立审查及适用 CI、且在现有合并授权范围内**的 PR；编排者无需逐次重新排序。每次合并前，必须针对最新目标分支与 PR 当前 head SHA 重新核验审查、CI、依赖、冲突和授权，并记录合并结果。审查失效、实质冲突、风险升级或授权不足时暂停相关 PR 并报告；高风险 PR 仍须针对本次 PR 与当前提交单独授权。“继续”不自动扩大已有授权范围。
